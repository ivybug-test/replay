# Replay 独立 OSS 后端需求

- 记录日期：2026-09-04
- 状态：需求范围已确认，待设计与实现
- 本文记录需求，不代表后端已经实现或服务已经切换。

## 1. 目标与背景

Replay 当前通过旧 `oss-replay` 服务获取实验、执行记录和回放数据。
旧项目同时包含前端、后端、聊天助手及分析功能，不适合作为新后端的长期运行依赖。

新后端直接读取 OSS，为 Replay 提供执行记录查询和回放数据。
第一版应支持现有实时与历史回放，并解决前端任务详情页无法关联 OSS 执行记录的问题。

当前前端已经有 107 道 OSWorld 2.0 任务及其能力标签、难度。
这些任务定义继续由前端管理，不迁入新后端，也不要求上传 OSS。

## 2. 职责边界

| 前端负责 | 后端负责 |
|---|---|
| 任务目录、题目说明、能力标签、难度、应用信息 | OSS 实验目录与任务执行记录 |
| 展示和筛选任务 | 按任务编号查询跨日期、跨批次的执行历史 |
| 任务卡片、执行表格、回放界面 | 读取轨迹、截图、评分和执行状态 |
| ATIF 增量合并、ATIF → UI 展示映射 | 存储格式解析、历史兼容及轨迹统一为 ATIF |

后端只需知道任务编号及其执行关系，不需要读取 OSWorld 任务源码、维护题目数据库，
也不需要提供任务定义列表或任务定义详情接口。

不包含：前端页面托管、聊天助手、分析会话、报告生成、任务执行调度、OSS 写入或删除。
前端静态文件服务及 API 代理的部署方式另行确定。

## 3. 标识和关系

| 标识 | 含义 | 示例 |
|---|---|---|
| `task_id` | OSWorld 原始任务编号 | `003` |
| `batch_id` | 一次批量实验，当前界面通常称为 run | `20260904T…` |
| `task_key` | 批次中的具体任务执行项 | `0001-003` |

一次任务执行由 **`batch_id + task_key`** 唯一定位。

- 一个任务编号可以对应多个批次、多个执行项。
- 一个批次可以包含多个任务执行项。
- 同一任务的多次尝试必须分别保留，不能按 `task_id` 覆盖。
- 不根据标题、相邻时间或模型名称猜测任务对应关系。
- 查询和传输应保留原始标识；任务编号的格式归一化规则需明确约定并测试。

前端已有的任务 ID（如 `osworld-v2-003`）不是 OSS 执行标识。
前端通过 `metadata.osworld_task_id` 取得原始编号进行查询。

## 4. 接口能力

第一版优先沿用已有回放接口路径，新增按任务查询执行历史的接口。
轨迹由后端统一为 ATIF；前端不再依赖 Agent Work 格式。
以下路径记录当前约定；分页参数、筛选参数及完整响应结构在接口设计阶段补充。

| 能力 | 接口 | 主要返回内容 |
|---|---|---|
| 实验列表 | `GET /api/runs` | 批次名称、时间、状态、任务数量；支持日期查询 |
| 实验详情 | `GET /api/batch?run=…` | 实验配置及各任务执行摘要 |
| 任务执行历史 | `GET /api/task-runs?task_id=…` | 跨日期、跨批次的执行记录；支持分页、模型和状态筛选 |
| 完整轨迹 | `GET /api/trajectory` | 原生 ATIF 或后端从历史格式转换得到的 ATIF |
| 实时轨迹 | `GET /api/atif-live?after=…` | 增量记录、游标信息、终止状态 |
| 过渡兼容接口 | `GET /api/agent-work` | 已有 Router 暂留；前端迁移到统一 ATIF 后退役 |
| 回放时间窗口 | `GET /api/window` | 时间范围、桌面帧索引及时间轴信息 |
| 桌面截图 | `GET /api/frame` | 指定帧的图片字节 |
| 模型或工具图片 | `GET /api/model-image` | 模型输入、工具结果等图片字节 |
| ATIF 图片资源 | `GET /api/atif-media` | ATIF 中引用的图片字节 |
| 执行状态 | `GET /api/execution-state` | 目标、行动、检查点、失败、恢复等结构化事件 |

除实验列表和按任务查询外，执行相关接口使用 `run=batch_id`、`task=task_key` 定位。
图片接口另外携带帧编号或资源路径等参数；时间窗口接口继续保留相应时间参数。

### 4.1 按任务查询执行历史

前端调用链：

```text
打开任务 osworld-v2-003
  → 读取 metadata.osworld_task_id = "003"
  → 查询该任务的执行历史
  → 展示批次、模型、状态、评分、时间
  → 选择一次执行
  → 按 batch_id + task_key 加载回放
```

每条执行摘要应包含：

- 批次 ID、批次名称、执行项 key、原始任务编号。
- 模型与执行框架信息（来源未提供时应明确缺失）。
- 执行状态、评测状态、Agent 声明的结果及评分。
- 开始时间、结束时间，以及可获得的耗时。
- 可获得的错误信息。

查询需要有稳定排序、分页信息和索引同步状态。
打开任务详情不应提前加载所有执行的完整轨迹或图片。

### 4.2 状态与错误语义

- 执行状态、评测状态、Agent 声明的结果、评分分别保留。
- 未产生评分不能当作零分，执行结束不能直接当作评测通过。
- 区分资源不存在、OSS 访问失败和数据解析失败。
- 索引仍在同步或同步失败时，不能只返回一个看似完整的空列表。
- 请求中的标识、游标、时间范围和分页参数需要验证。

## 5. OSS 读取与查询索引

后端只需要 OSS 的分页 List 和 Get 能力。

| OSS 交互 | 目的 |
|---|---|
| 按前缀和分隔符分页列举批次目录 | 发现新实验和历史实验 |
| 读取各批次的 `batch.json` | 提取执行摘要，建立任务与执行的对应关系 |
| 读取完整轨迹或实时流清单、分块 | 提供历史与实时回放 |
| 按需读取图片、结果和状态文件 | 支持回放及评分展示 |

实验发现与执行历史查询不能依赖扫描全部轨迹、截图或下载图片字节。
没有截图的合法实验也应能够被发现。

需要维护一个**可从 OSS 重建的执行摘要索引**：

- 只记录从 OSS 提取的批次、任务编号、执行项和必要摘要。
- 覆盖历史日期，不能只关联当天的 runs。
- 增量发现新批次，刷新进行中执行及后续评分变化。
- OSS 是原始数据来源，索引是查询加速层。
- 对外提供同步中、可用、同步失败等可辨识状态。
- SQLite 可作为实现选项，具体存储、同步频率及恢复机制在设计阶段确定。

## 6. 轨迹和图片兼容

目标数据链路：

```text
原生完整 ATIF ───────────────→ 后端校验 ─────────────┐
原生实时 ATIF 分块 ──────────→ 后端解析与校验 ───────┤
旧 runtime-trace → 后端解析 Agent Work → 后端转 ATIF ┤
                                                    ↓
                                     统一 ATIF 文档或 ATIF 增量
                                                    ↓
                                前端合并增量、atifToViewer → 展示
```

- 后端统一负责源格式选择：优先采用已发布的完整 ATIF；发布前读取原生实时流；
  历史日志转换为 ATIF。Agent Work 可以作为后端内部中间结构。
- 将 `src/lib/legacyTraceToAtif.ts` 的转换语义迁入后端，参考现有实现和样本验证一致性。
  `src/lib/atifToViewer.ts` 继续留在前端，负责展示结构转换。
- 前端只消费统一 ATIF 文档或 ATIF 增量，负责增量合并和 UI 展示；
  不承担历史格式识别、Agent Work → ATIF 转换或 OSS 路径兼容。
- 后端 parsers 采用纯解析/转换函数，与 HTTP、OSS 访问和缓存隔离。
  实时清单与分块校验、旧日志解析、Agent Work → ATIF 转换均属于该目录。
- `/api/agent-work` 仅记录现有 Router 的过渡状态，不作为目标前端的必需接口。
  后端转换、前端消费逻辑和旧接口退役应配套迁移，切换前保持现有回放可用。
- 支持已有的不同轨迹存放路径，具体规则以现有 OSS 数据契约和样本验证为准。
- 实时游标、刷新和完整轨迹接管不能造成步骤丢失或重复。
- 截图时间、轨迹时间及执行状态继续使用已有回放时间语义。
- 桌面截图、模型输入图片、工具结果图片均需可读取，不能只验证文本轨迹。

已确认的主要存储位置包括：

```text
<OSS_PREFIX>/harness/<batch_id>/
├─ batch.json
└─ tasks/<task_key>/
   ├─ trajectory.json
   ├─ agent/trajectory.json                 # 其他已支持的轨迹位置
   ├─ runtime-artifacts/trajectory.json
   ├─ trajectory-tail.meta.json
   ├─ trajectory-tail.jsonl.chunks/
   ├─ runtime-artifacts/runtime-trace.jsonl # 历史格式
   ├─ trace-tail.meta.json
   ├─ trace-tail.jsonl 或其分块目录
   ├─ replay/meta.json
   ├─ replay/events/
   ├─ replay/frames/
   ├─ run_state.json
   └─ result.json
```

上述文件并非每次执行都会同时存在；还需遵循批次元数据中的执行目录约定。

## 7. 独立运行和资源约束

- 新后端独立启动，不依赖旧 `oss-replay` 进程或其代码目录。
- OSS 凭据只保留在后端，不进入浏览器、接口响应或错误日志。
- 图片和资源读取限定在对应执行目录内，不提供任意 OSS 路径访问能力。
- 缓存容量、并发读取数、单次读取与响应大小需要明确上限。
- 明确处理超时、上游故障和无效参数。
- 提供健康检查和足以诊断同步、读取故障的运行信息。
- 部署及切换应保留现有服务的可用性，并与当前主机资源保护机制协调。

## 8. 验收标准

1. 任务 `003` 等已有执行的任务，能够查到不同日期、不同批次中的执行记录。
2. 同一任务多次执行分别保留，查询结果能够分页和筛选。
3. 从前端任务详情点击某次执行，可以进入正确的回放页面。
4. 原生完整 ATIF、原生实时 ATIF、旧版日志的代表性样本均通过统一 ATIF 契约回放；
   前端无需执行 Agent Work → ATIF 转换，迁移后步骤、工具调用和图片语义保持一致。
5. 实时刷新和完整轨迹接管不丢步骤、不重复追加，时间轴保持正确。
6. 桌面截图、模型输入图片、工具结果图片及执行状态可用。
7. 评分缺失、评测进行中、执行失败等情况不会被混淆。
8. 索引初次建立、重启、同步失败和 OSS 读取失败有明确状态，不误报“没有 runs”。
9. 前端任务说明、能力标签和难度继续正常显示，不依赖后端存储任务定义。
10. 验证新后端运行期间不调用旧 `oss-replay` 服务，也不从旧项目目录导入模块。
